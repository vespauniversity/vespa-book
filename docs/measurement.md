## Decided

- Corpus preset: **`book`** (decided at the end of the probing phase) — 3,500 hard US queries (train 1,750 / validation 750 / test 1,000), 100,000 products (≈67k judged + ≈33k distractors), seed 42, gains `kdd`. Needs `corpus.py` preset + validation fraction 0.3.
- Metric set: **ndcg@10** (headline, gains `kdd`), **recall@10**, **recall@100**, **mrr**; every difference as `metrics.bootstrap_delta` with the verdict word. Extras: ANN **agreement@K vs exact search** (ch4 HNSW, ch8 filtered ANN — a system property, no judgements needed); **overlap counts** found-by-both / keyword-only / vector-only / neither (ch4, exact counts, no interval); **task success rate** with a binomial interval (ch11); **own-profile vs shuffled-profile** paired delta (ch10). No interval is computed for recall today — a recall bootstrap is a ch3 step-3 candidate.
- Latency method: warm pass (discarded) + 3 measured passes, median p50 / p95 client-measured; p99 only if 3-pass jitter <30%; never Vespa's `searchtime` (whole-ms, excludes query embedding). Condition sentence: *Cost, one machine: Apple M4 Pro, a 4 CPU / 10 GB container VM (Rancher Desktop), median of 3 warm passes, client-measured, <split> split, N queries — a reader's machine gives a different number.* (Q4; runtime named per D126)
- Memory method: `memory.py --settle 600 --rounds 3 --tolerance 0.01`; report `allocated_bytes` for the document type, explained in plain words; settled = two readings ≥10 min apart within 1% (Q5)
- Feed method: `feed.py`, concurrency 16, reports documents / failed / retried / seconds / docs_per_second; expected ≈3 min plain, ≈8 min with embedder at 100k (Q2).
- Per-chapter extras: ch3 profile table (Q13); ch4 overlap + blind-spot reach + model trade-off (Q14); ch6 rerank-count curve (Q7); ch7 LTR vs tuned with feature importances (Q8); ch8 ladder × strategy × HNSW exploration, leakage = 0 (D23/D24); ch10 upper bound + second-order brand + shuffled control + negatives (Q15); ch11 oracle vs retrieved, k=3 vs k=20, shift A+B (D26–D29).
- Quality vs cost list: Phase-1 probe q12 (the maintainers' record, not shipped) — quality = ndcg / recall / mrr / counts / agreement / success rate (reader reproduces to three decimals); cost = latency, memory, feed and build durations, docs/s (ours, one machine, condition sentence from Q4 beside every one).

## Notes for the planning table (a maintainers' document, not shipped)

- Which lexical profile is the baseline chapter 4 beats changes the size of the semantic win (+0.029 vs `bm25_title`, +0.054 vs `bm25_weighted`). Chapter 3 must end on the profile chapter 4 uses. (Q1 side finding 2)
- Q13 answers it: chapter 3 can end on a *tuned* BM25 (k1 0.6 for short titles + exact-match boost), which beats title alone by +0.017 real on test in the chapter (+0.019 in the probe) and the old field-weighted profile by +0.034. Field weights on bullets/description/brand lose. Decided so: the semantic win in chapter 4 is measured against the tuned profile (it reads ≈ +0.01–0.02 at this resolution).
- Q3: validation is a few points easier than test on label mix in both builds. Every "validation says / test says" pair in the book should be read with that in mind; it is a property of ESCI's official split, not of our carve-out.
- Q9 (ch8): brand is too fine as a tenant for a selectivity ladder at 100k docs. Two honest ways out, to decide at the `synthetic-data.md` sign-off: (a) a ladder from *existing* attributes — `has_description` (~50%), brand present (~95%), marketplace tenant (5.3%), a single brand (0.6%), a small brand (0.01%) — 4 orders of magnitude without inventing anything; (b) note that filtered-ANN **recall vs exact search** is a system property measurable on any query, so it does not need judged products inside the filter — only relevance numbers under a filter do, and those are thin (10–16 queries).
- Q10 (ch10): connected components over shared E products give users of 1–8 queries and 63–173 held-out queries in total: recommendation quality cannot be measured to Q1's standard with that definition. Options for sign-off: derive users from brand affinity (queries whose E products share a brand → many users with more queries each), or state plainly that ch10 measures the mechanism (partial updates, profile tensor, freshness) and reports recall@K over users with its wide interval.
- Q11 (ch11): 680 test questions at threshold 3; a task-level success rate resolves differences ≥ ~0.08 only. Fine for oracle-vs-retrieved (expected large); not fine for comparing two retrieval settings. The distribution-shift statistic (heading 7) is undefined and needs a decision.
- Q6: `feed.py` report must record `--batch-size`, `--limit`, `--label`; `main()` needs a test. Goes to ch02 step 3.
